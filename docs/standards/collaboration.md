# 协作与进度同步规范

本规范约束成员与AI助手。共享状态统一维护在 [docs/project-status.md](../project-status.md)；OpenSpec负责具体需求和验收标准，进度表只记录实际推进情况，不能代替规约、测试或批准。

## 1. 一个变更，两个人接力

- 规约与终审人：写 proposal、design、spec、tasks；说明范围、失败场景和验收条件；实现后读代码并亲自复跑关键场景。
- 规约评审与实现人：先审规约，指出含糊或无法验证的要求；确认后执行apply，补测试、自检、提交证据并修复问题。
- 规约PR由实现人审，代码PR由规约人审；第三人推进自己的变更，不是固定的额外批准人。成员不固定负责某个技术模块。
- 审查者发现问题后直接在原PR来源分支修复规约/代码，补必要验证、同提交更新共享表，复核最终差异后正常合并；可以合并自己在审查阶段的修正，不再强制退回原作者或增加一轮反向审查。涉及需求变化先同步规约，尚未明确的公共契约不能由实现猜测。
- AI可辅助写作、实现和审查，不能冒充另一位成员批准。远端保护要求照常遵守；若与两人安排有冲突，先明确处理方式，不绕过门禁。

### 审查者直接修复的执行细则

2026-11-05起，依据组长明确指示“审查之后，审查者直接修改，然后提交，合并这些，这是之后的规则了”，第1节的新流程适用当前未合并PR和后续工作，替代旧的修复后强制交搭档再审规则。已归档历史、原批准人及原测试结果不追改。

- 开工前获取最新远端，保留未提交修改；在原PR继续，不为每轮意见新开PR、不强推覆盖同伴提交。
- 记录实际审查人、问题、修复提交、最终head、命令/结果及剩余依赖；自己的账号记录自己的判断。GitHub不允许自审时使用明确的收口评论，不伪造另一成员APPROVE，也不把旧review说成对新head的批准。
- 最终head检查通过、冲突解决、对应G2/G3及实际依赖满足后，绑定预期head正常合并。远端强制审核/检查仍须满足，不使用管理员绕过；合并后记录实际main SHA，必要时复验。合并不等于实现或归档完成。
- 当前积压PR由组长授权小张依据已有真实评审接手修复、验证和集成，以小张身份说明承接范围；不冒称小葛/小陈作了新批准。后续默认由对应变更的实际审查者收口，人员不固定技术模块。
- 公共契约或范围变化先修OpenSpec及单源合同，给出选择、影响与验收；尚无依据的业务决定仍须澄清。共享表、测试、安全、独立会话真实性和实际依赖不因简化交接而免除。

## 2. 什么时候更新共享表

| 时机 | 谁更新 | 必须写什么 |
| --- | --- | --- |
| 开始工作 | 当前执行者 | 变更编号、角色、实际进入的阶段、前置是否满足 |
| 代码/测试/配置/脚本形成提交 | 修改者 | 同一提交更新对应行；记录本次实际改动、验证结果和下一步，即使阶段没变 |
| 提交规约或交接PR | 提交者 | PR链接、交给谁、希望对方检查什么；尚无PR就写未创建和分支名 |
| 完成评审或直接修复 | 实际评审者，或据其真实记录更新的搭档 | 审查记录、修复提交、最终验证及合并/阻塞结论；不得推测或代填批准 |
| 遇到阻塞/解除阻塞 | 发现者 | 缺什么、等谁、解除条件；解除后更新进展 |
| 集成验收/完成/重新打开 | 两人核对，由规约与终审人收口 | 版本、实际结果、证据链接；发现缺陷后回退到真实阶段 |

“每次修改”按一组可提交的工作计，不要求每敲一行代码就改表。AI助手在结束工作或交付未提交改动前，也必须同步表格；验证未运行就写“未验证+原因”。后续得到新的验证结果要及时补写，不能沿用旧的通过结论。

开工或验收改变整体阶段时，同时更新表顶部“现在做到哪里”和里程碑；README中若有对应现状也一并修正，避免上面写未开工、下面却已完成。

纯排版且不影响计划、角色、状态的文档修正可不改变业务行；影响规约、计划或验收的文档修改必须同步。本次协作规范维护放在表中的“流程维护”行，不冒充业务00已开工。

不要在正在生成的提交里填写它自己的SHA；本次结果可写“本提交”，由Git历史定位。PR/验收证据要标明实际验证的代码版本、命令、结果、退出码及环境；无执行结果不得写通过。

## 3. 阶段怎么判断

| 阶段 | 进入条件 / 下一步 |
| --- | --- |
| 未开始 | 计划已登记，尚未实际编写规约；等待依赖不代表已经开工 |
| 写规约 | 规约人开始写四份文件；写清正常、失败和边界场景 |
| 待审规约 | 规约已可审，交给实现人；意见未解决不能apply |
| 实现与自测 | 规约已确认、严格校验通过、实现前置满足；实现人写代码并验证 |
| 待终审 | 实现人完成应做的自检并提交当前版本证据；规约人审查及复测 |
| 待集成验收 | 当前实现评审通过，尚需真实依赖或合入后的集成版本验收；此时仍未完成 |
| 已完成 | 当前变更规定的验收通过、评审问题关闭、按门禁合入；需归档的也已归档，证据可追溯 |

阻塞写在“卡点”列，保留真实阶段；不要用阻塞掩盖还没做。返工回到“写规约”或“实现与自测”并注明原因。mock自测、CI通过、PR合并各自只说明相应部分，不能单独作为整个变更完成的依据。纯文档变更按文档的验收条件执行，不强行编造运行测试。

## 4. 并行开发时怎么维护同一张表

1. 从团队约定的集成基线创建自己的分支，通过PR交接。先读共享表与本变更规约，只在约定接口明确后并行实现；公共契约变更先列出受影响变更并同步搭档。
2. 每个分支只修改自己相关行，保留其他行。共享表是唯一进度台账，不再另建长期维护的个人总表；各OpenSpec的tasks仍维护本变更细项，勾选情况须与台账一致。
3. 默认分支上的表代表已合入的状态，各活动PR中的对应行代表尚未合入的最新进展。开工/等待审查等更新可先提独立进度PR；群内交接必须附活动PR或分支，避免把默认分支的旧状态误当最新。代码PR仍须携带自己对应行的更新。
4. 合并前获取最新集成状态，逐行核对。冲突时不能整文件选“用我的/用对方的”；依据实际PR、测试和时间合并各行。相同一行由两位负责人确认最新事实，不按谁最后推送决定。
5. 合并与验收后的状态若未包含在代码PR里，及时补一个进度更新PR。不能提前写“已合并”“已完成”；若本次合并改变了代码，受影响的验证需重跑。
6. PR审查包含进度表检查。缺失或失真先补正再通过。本次规则由AGENTS提示、成员与PR清单落实，尚未新增自动检查“代码提交是否同步表格”的CI，不能声称已有自动拦截。

## 5. 每天与每次交接怎么说

每天收工前，各自在群里发三句话；不要只报百分比。有人等你审查时，优先处理交接。群消息用于提醒，结论与证据仍回填仓库。

```text
今天：变更XX，做完了什么，目前处于什么阶段；PR/分支：……
下一步：谁做什么；需要对方审哪部分。
卡点：缺什么、等谁、什么条件满足就能继续；没有则写无。
```

四个整体里程碑是“规则定好 → 分项开发 → 系统接通 → 交付完成”，按共享表中的可验证条件更新，不以代码行数或主观百分比判断。可以提前准备后续规约，但未通过前置验收不能宣布后续里程碑完成。

第7课历史规约、A/B/C记录和未结项保留原义；本规范不追溯改写其批准、验收、归档状态，也不授权提前突破当前仅骨架的业务约束。
