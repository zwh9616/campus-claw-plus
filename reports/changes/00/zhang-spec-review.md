## 必须修订的问题

### R1 / P1：截止检查与幂等重放的先后顺序冲突

位置：`design.md:41`，关联BC-04 / BC-SC-07。

反例：学生在截止前提交，submission/outbox已成功提交事务，但202响应丢失；截止后以同键同载荷重试。该段既要求“服务端时间>=deadline即409”，又要求同键同载荷返回原202，两种实现都可声称遵守文字，却给前端不同结论。assignment_version后续变化也有相同优先级问题。

建议：明确认证和资源授权始终重新检查；对已提交的幂等记录，是否先核对作用域/摘要并重放受理结果，再仅对新请求执行截止和版本校验。明确202中的pending是原始受理快照，当前状态由task查询获得，避免已完成任务被UI误判为重新排队。由规约人确定最终顺序，不能由apply自行选择。

关闭条件：补“截止前成功但响应丢失→截止后同键重试”“同键异载荷”“新键截止后提交”“权限已撤销后重放”四个场景，给出唯一HTTP/业务码和新增submission/task/outbox数量判据。

### R2 / P2：SSE恰一个终结事件与取消/断网规则没有接合

位置：`design.md:51`、`:53`，关联BC-04 / BC-SC-08。

当前要求每条流恰好以done或error终结，但取消只规定关闭上游、持久化cancelled且不发done，未定义是否发error、错误码和retryable。断网时又不能保证终结帧送达。客户端据此无法区分主动取消、网络中断和服务故障，也无法确定重连查询应怎样清除加载状态。

建议：分别定义连接仍在时取消的终结事件/字段、连接已断时不保证帧送达而以持久化查询为准、完成与取消竞争时的终态优先规则。可选error/CANCELLED方案，但需要小葛明确确认；同时给出partial与failed的区别。

关闭条件：连接中的取消、断网、取消与完成竞争、已完成后再次取消均有唯一事件序列和持久化状态，终结后无token，不重复付费调用。

### R3 / P1：下游apply准入没有区分00规约批准与00实现落地

位置：`design.md:69`至`:72`、`:81`、`:94`，关联BC-05/06 / BC-SC-09/11。

D8的01/02/03/10仅写“00确认”，BC-SC-11也只阻止00未经规约审查的情形；但PB-09 delta明确要求00“批准并落实后”，Migration Plan要求00落地前继续执行现行仅骨架规则。若小张一批准规约就让下游apply，机器合同和规则尚未合入，便会在旧规则下开始业务实现。

建议：给00定义两个可引用状态：规约确认允许小张实施00；00合同/规则实现经小葛终审并合入集成基线，才允许下游业务apply。若确需叠加分支开发，明确允许范围与所依赖提交，不能把它写成已具备合并条件。统一说明10的前置门禁覆盖所有业务PR，避免02等行漏写而被理解成例外。

关闭条件：给出“只有00规约批准、没有00实现合入”的反例，01/02/03/10均不得进入业务apply；D8、PB-09 delta、BC-SC-11及tasks使用相同准入词和证据条件。

### R4 / P2：OpenAPI与JSON Schema版本混用，缺少转换或共享方式

位置：`design.md:15`，关联BC-01 / BC-SC-02。

D1同时指定OpenAPI3.0.3和JSON Schema2020-12，并要求示例由相同Schema验证，但没有规定两种方言如何对应。OpenAPI3.0.3并不直接接受任意2020-12 Schema；例如nullable及多类型表达不同，直接把2020-12文件作为Schema引用可能使文档工具和JSON验证器得出不同结论。这是合同设计缺口，不是声称当前尚未生成的文件已经校验失败。

建议：选择支持2020-12的OpenAPI3.1版本并明确工具支持，或保留3.0.3但定义唯一源、生成/转换规则、允许的共同子集与双端一致性检查。两者选其一，由小葛确认，不能手工维护两套看似一致的Schema。

关闭条件：给可空字段、额外字段、枚举、引用的正反例；承诺OpenAPI校验、Schema校验和同一批样例结果一致。语义规则（总分求和、rubric对应等）另列检查，不假定普通Schema能验证跨字段业务关系。

依据：[OpenAPI3.0.3 Schema Object](https://spec.openapis.org/oas/v3.0.3.html#schema-object)、[OpenAPI3.1.0 Schema Object](https://spec.openapis.org/oas/v3.1.0.html#schema-object)。

### R5 / P2：宣称冻结的接口仍缺少可生成合同的响应或状态字段

位置：`design.md:29`、`:37`、`:43`、`:45`、`:53`，关联BC-01/03/04。

BC-01要求冻结字段和端点，但refresh没有明确响应结构；materials列表的items没有Material结构；PUT grade没有成功状态码/响应；GET turn只描述“状态和已持久化文本”而未给字段名和完整结构；Task允许显式重试/取消但没有请求入口与输入输出。00实现人无法在不新增业务决定的情况下生成这些OpenAPI响应及客户端测试样例。

建议：新增“本轮冻结/留待后续细化”的端点矩阵。立即供01/02使用的会话响应必须补全；其余明确标待定义、责任change及冻结前禁止接入，不生成空对象或任意object冒充稳定合同。D1的全部对象additionalProperties=false也应落实到Audit.usage等嵌套对象，或明确合法扩展边界。

关闭条件：每个声明已冻结的端点有输入、成功/失败响应、权限和至少一组样例；待定义接口有负责人和阻塞依赖。小张无需口头补字段即可转为机器合同。

### R6 / P2：任务租约重投缺少旧执行者失效的规则

位置：`design.md:43`，关联BC-04 / BC-SC-07。

反例：worker A因暂停/网络延迟超过60秒租约，任务被worker B接管；A随后恢复并提交旧attempt结果。现有“DB去重、结果唯一”只能约束条数，没有明确哪一代执行有权提交，旧结果仍可能抢先落库或覆盖重试后的状态。running取消与成功同时发生也缺少裁决规则；“总最多3次”是否包含首次及崩溃重投不明确。

建议：明确提交结果必须匹配当前执行代次/租约所有权和允许状态（具体锁或CAS实现留给05/08）；过期执行者不能改变任务、成绩或outbox。补attempt计数起点、自动重投/手动重试如何消耗次数，以及取消与成功只能原子地产生一个终态。

关闭条件：在05/08必验清单登记“租约过期后旧worker恢复”“同一attempt重复结果”“取消和成功竞争”“达到上限再重试”用例，预期明确到任务状态和数据写入次数；00本轮只验证合同完整性，不要求现在实现worker。
