## Context

组长明确指示：“审查之后，审查者直接修改，然后提交，合并这些，这是之后的规则了”。当前00已进入main且G2成立；01/02/10仍有规约或依赖待办。新流程适用于未合并PR及未来工作，不修改历史作者、批准或失败记录。

## Goals / Non-Goals

目标是让实际审查者把可确定的修复做完并收口。不是免审、免测或跳过公共契约；不是让原作者冒充另一成员，也不把规约合并当业务上线。

## Decisions

1. 两位负责人仍按原表接力：规约由实现人审，代码由规约人审。审查者直接改原PR、补必要验证、同提交更新共享表，不因自己修复再要求作者反审。
2. Git操作先核对远端及未提交修改，禁止覆盖同伴工作或强推。范围不清先修规约/确定公共合同，范围内的具体修复由审查者完成。
3. 使用实际账号记录问题、修复提交、最终head和命令结果。旧review可作问题依据，不能改写成新APPROVE。平台不允许自审时用明确收口评论；远端强制其他审核时仍满足该条件。
4. 检查通过、无冲突、对应依赖满足后按预期head正常合并，不用管理员绕过。合并后跟踪实际main SHA及必要复验，不提前写已完成。
5. 本次组长授权小张承接积压PR已有真实评审的修复与集成；需明确注明其承接身份。未解决公共依赖保持可见，不为赶合并伪造决定。

## Risks / Trade-offs

减少一次独立再审意味着修复者承担最终差异核对责任；使用可追溯head、必要检查和共享进度降低漏项风险。用户没有撤销远端保护或业务G2/G3，不扩大本授权。

## Migration Plan

一次同步AGENTS、协作规范、PR模板、00依赖说明与本规约；历史archive及真实结果保留。既有change中“修后再交作者”的流程文字按此用户新规则解释，但其中的实际技术判据和依赖继续适用。验收为文档一致性、严格规约及当前PR真实处理记录，不生成运行代码测试。
