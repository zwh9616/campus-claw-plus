### D2 统一入口与失败传播（A）

沿用 npm 作为检查逻辑唯一入口，Makefile只是薄封装；不采用第二套脚本重写断言。建议映射：make setup → npm ci 后 npm run setup；make check/audit/secret-scan/verify → 对应 npm run；make gate → npm run gate。新增 npm run gate 串行执行 check → audit → secret-scan → verify，任一非零即停止并非零退出；原 npm run check 子项、原 npm run verify 和所有原断言必须保留。禁止 || true、忽略错误的make前缀、continue-on-error、空成功替身、只打印命令的dry-run当验收。并行make调用不得绕开串行gate顺序，重复验证使用独立Compose project/端口并在finally清理自身资源。

CI沿用既有 .github/workflows/check.yml 的 job check 作为稳定required context；保留npm ci/setup及全部既有检查，可将相同序列委托make gate，但须逐条对照证明覆盖与失败传播没有减少。PR（含仅文档）、main push均触发，不用paths过滤跳过required检查；不得改名导致旧保护失效。固定Actions SHA、最小contents:read、20分钟超时、并发取消旧运行保留；取消/超时/安装失败/没运行均不视为通过。npm命令仍可在Windows直接运行；make不可用时文档指出需安装GNU Make，并提供等价npm gate，不静默跳过。

依赖以锁文件精确安装；Node满足00最低22.19.0、Go固定工具链沿用toolchain.json。audit仍high/critical阻断，secret scan全历史+暂存，容器verify保留真实退出码。正常gate不访问付费模型或生产业务数据。

### D3 真实保护与受控红绿（A）

main必须要求PR、至少1位非PR作者批准、关键更新撤销旧批准、required check（GitHub Actions实际check context及来源app，记录实际名称/ID）、与main保持更新；管理员同受约束，不配置可绕过失败检查的成员/机器人例外，不允许force push/删除。可用branch protection或等价ruleset，保存实际有效配置；不可只提交一份建议JSON。若套餐/权限不支持，A阻塞，管理员处理权限/仓库设置后重验，不能写G3通过或用口头纪律替代。按2026-11-05组长新规则，不将“最后推送者之外的人再批准”设为额外必需条件：非PR作者的审查者可直接提交修复，再以自己账号对最终head重新批准并合并，无须把修复退回原作者；旧批准不能替代新head审查。若当前远端已有更强制设置，仍须满足或经明确授权调整并留证，不能绕过。

### D4 服务接线与健康边界（B）

使用现有compose.yaml增量接线，不额外创建第二套部署入口。逐项登记服务change/集成SHA、镜像摘要、网络、必需/可选依赖、active配置键、健康探针、超时及故障回退；可先接身份/数据库，随后检索/队列worker/MCP/模型适配器，顺序依相应change批准，非本规约授予提前apply。真实值仅运行时.env或受控secret注入，样例只含登记空键；不在ARG/镜像层/前端/日志/报告出现值。

当前health原样回归。新增依赖前由所属change修订00机器合同及probe/test/规则并两人确认；未冻结不新增业务operation。必需依赖down的受影响业务/readiness返回约定503，恢复后再放流；存活与就绪语义明确，不能因可选LLM不可达阻断无需LLM的浏览。不要在10自行猜新的健康URL。探针须限时（单次至多3秒、一次部署等待至多120秒），超时非零，容器running不等于ready；现有更严格条件仍保留。MCP精确候选仍须03/07C批准和实际网络核验，不能开放通用私网段。

### D5 观测、审计和告警（C）

不在A安装监控栈。C实现采用结构化日志及内部受控指标采集；指标端点/采集权限如需新增HTTP须先冻结合同，不对外公开原始运维或学生数据。保留ts/level/module/message/request_id及HTTP的method/path/status/duration_ms，跨HTTP/任务/工具复用关联标识，禁止正文、查询串、凭据或学生原值。标签只用规范路由/方法/结果/依赖服务等有界枚举，禁止user_id/class_id/request_id作指标标签，未知路由聚合，Nginx秒与Go毫秒不混算。

请求量计实际完成HTTP次数；HTTP 5xx/全部完成HTTP作为错误率；p95采用完成请求耗时毫秒（含4xx，分业务路由；SSE持续时间另列不混入普通HTTP），5分钟窗口滚动计算；窗口无请求标no_data，不记0成功、不计算错误率/p95，也不计入健康恢复窗口；非空窗口无最低样本豁免，1..19样本附insufficient_data质量标记，但仍计算并按相同阈值告警，20及以上标记sufficient_data。p95按nearest-rank取排序后第ceil(0.95*N)个值（从1计数），用于固定时间的可重复边界验证。依赖状态按有限时探针记录；告警为5分钟错误率>5%、普通HTTP p95>500ms或同依赖连续失败3次；等于阈值不触发，依赖一次成功清零。连续3个健康窗口恢复，依赖连续3次成功恢复；同一规则/服务/环境去重15分钟，但仍累积事件并记录恢复。固定时间的规则单元测试覆盖下表，不靠真实sleep；20样本仅为质量标记分界，不修改现行部署规范的告警触发条件。

| 五分钟窗口输入 | 预期结果 |
| --- | --- |
| 0个请求 | no_data，错误率/p95不计算、不发这两类告警、不计健康恢复；依赖探针独立判定 |
| 19个请求全部5xx，耗时均100ms | insufficient_data，错误率100%仍告警；p95=100ms不触发耗时告警 |
| 20个请求全部5xx，耗时均100ms | sufficient_data，错误率100%告警；与19样本无豁免差异 |
| 20个请求1个5xx/2个5xx，耗时均100ms | 错误率5%不触发/10%触发 |
| 19个请求均2xx、耗时均500ms/501ms | insufficient_data；p95=500ms不触发/501ms触发 |
| 20个请求均2xx、耗时均500ms/501ms | sufficient_data；p95=500ms不触发/501ms触发 |
| 依赖连续失败2次/3次（无论HTTP样本量） | 不触发/触发依赖告警；一次探针成功清零连续失败计数 |

演练只向事先获授权的测试接收端发送，未配置接收端明确告警投递失败并保留重试/人工处置记录（3次、指数退避1/2/4秒，达到上限明确失败），不伪称送达；负责人按当周实际值班登记，恢复流程主责小陈但不固定全部技术工作。C验收要真实故障、收到一次告警及恢复通知；测试接收端与生产通知明确区分，不在本规约PR实际发送。

按00公共审计要求，审计不可用时高风险写入拒绝503且无业务副作用；普通授权读取允许返回但有运维事件。可靠持久化的存储/重试/容量由对应已批准实现设计收口，C必须注入故障验证，不用日志打印冒称审计落库。

### D6 最终运行与恢复（C）

同一候选SHA在干净目录，按README安装、空值配置校验、Compose构建/启动、实际healthy、授权主路径、日志关联、停机/再启动；保留现有10秒应用排空/15秒Compose宽限、端口占用与非法配置反例，不停止其他项目。隔离卷/项目名/端口，演练前确认绝对路径及资源标签，不能删除生产或无关资源。

有持久数据后每日MySQL备份及Qdrant快照，保留7天，受控访问/加密存储，凭据与学生正文不进入Git。RPO≤24小时、RTO≤60分钟，从宣布故障至服务健康和授权数据校验完成计时；隔离实例实际恢复，核对记录数、代表性版本/出处、权限及任务幂等，不只断言文件存在。模拟损坏备份应明确失败且不覆盖现用数据；无备份/超过RPO不宣称恢复合格。模型/MCP自身可重建配置不等于持久库备份。

## Risks / Trade-offs

- [main不受保护/权限不足] → 记录管理员阻塞，G3保持未成立；当前不偷偷设置或绕过。
- [规约堆叠未合入导致链接/冲突] → 10从main独立起草，引用00固定版本；合并前逐行整合共享表，G2后重核合同，不整表覆盖。
- [入口重复或维护成本] → npm唯一实现、make薄包装；旧回归与新业务分别登记，CI与本地同入口。
- [红绿误伤/日志泄漏] → 隔离副本和测试PR、逐字节恢复、脱敏，禁止真正合并破坏提交。
- [监控范围扩大拖慢A] → A只交付门禁，B/C分批；不能将后两段不做变成整体完成。
